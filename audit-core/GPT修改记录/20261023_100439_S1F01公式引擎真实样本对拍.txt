【目的】
使用 Open-Data-Audit 的真实 S1 模板和批次输入，对 S1-F01 公式重算做真实样本对拍，并比较本机原生计算候选与 Office 引擎的结果和耗时。该实验只评估候选，不代表 S1-F01 已迁移或通过验收。

【修改文件】
- 新增本文件；没有修改业务代码、Cargo/Go 依赖、构建配置、生产默认路由、源 Python 项目或 workspace 其他文件。

【样本与方法】
- 来源：只读使用 Open-Data-Audit `config-real` 真实模板及 `2026-07-31` 批次中的一组结构匹配输入；文件名、工作表名、单元格地址、公式文本和业务值不写入本记录。所有运行输入均为系统临时目录中的副本。
- 模板覆盖 1,072 个公式单元格；S1 公式涉及 ABS、ADDRESS、AND、CELL、COLUMN、IF、IFERROR、INDEX、INDIRECT、ISNUMBER、MATCH、OR、ROUND、ROW、SUM、TEXT、VLOOKUP 等函数。待重算副本由既有 S1 规则复制生成，确认 1,072 个公式仍在，且有 373 个公式缓存为空；不以原缓存充当重算结果。
- 旧项目 Windows S1 路径按 `COM_RANGE` 跑完整 DAG；再以同一未重算副本，分别调用 Excel、WPS、Rust Formualizer、Go Excelize 和 Go Werkbook。候选计时均包含各自工具进程启动；Office 的多轮计时复用单个 COM 实例，另计其启动时间。
- 对拍以公式文本保持不变为前提；数值缓存逐格比较，数值允许相对误差不超过 1e-15，文本要求精确一致。S1 公式问题记录逐条比较。

【环境】
- Windows 11 x64；Microsoft Excel 16；WPS 表格 11.8.2；本机未发现 LibreOffice。
- WSL Ubuntu 24.04 / glibc 2.39 中也未发现 LibreOffice；本轮没有在麒麟 V10、统信 V20 或 glibc 2.28 环境运行。
- Rust 候选：Formualizer CLI 0.11.1。Go 候选：Go 1.27.3 + Excelize 2.11.0；Go Werkbook 0.11.0。对拍脚本使用原项目现有 Python 3.12.10/openpyxl 环境作文件读取与 COM 控制，只用于本次实验，不进入生产路径。

【旧项目完整 S1 基线】
- 一份实际输入完整跑通 S1 DAG：Microsoft Excel 单次观察 10.271 秒；WPS 单次观察 7.830 秒。两者输出均保留 1,072 个公式；公式问题记录各 26 条，逐条一致。缓存值比较为 1,071 格精确一致、1 格在 1e-15 相对容差内；公式文本一致。
- 完整 DAG 每个引擎仅跑一轮，以上时间是单次观察，不作为稳定性能结论。

【公式重算候选对拍和时间】

| 候选 | 每轮耗时（毫秒） | 中位数 | 对拍结果 | 评估 |
| --- | --- | ---: | --- | --- |
| Rust Formualizer 0.11.1 | 145.7、142.4、143.4、137.3、133.7 | 142.4 | 五轮均写回缓存，1,072 个公式文本无变化；1,071 格与 Excel 精确一致，另 1 格文本结果不一致；公式问题记录 25/26 条一致，1 条的结果文本和说明字段不同 | 未通过 S1 行为等价；不能据速度优势进入默认路由 |
| Go Excelize 2.11.0 `CalcCellValue` | 208.5、212.8、243.2、216.3、206.9 | 212.8 | 每轮 1,072 格求值中 217 格报错；在其余成功结果中有 43 格与 Excel 不同；探针只导出逐格求值 JSON，没有重算并写回整个工作簿缓存 | 不是可替换的整本重算路径 |
| Go Werkbook 0.11.0 | 213.7、198.3、210.8、203.8、228.8 | 210.8 | 五轮均写出工作簿、公式文本无变化；缓存中 484 格为公式错误，536/1,072 格与 Excel 不同 | 未通过；无法满足 S1-F01 重算契约 |

- Rust Formualizer 的单格文本差异在五轮稳定复现，并传导到一条 S1 公式问题记录，因此即使数值 token 的偏差很小，也不能按数值容差把文本输出判为通过。
- Go Werkbook 的公开公式目录将 CELL 列入“无计划支持”；这与本样本中的 CELL 公式使用相符，但本轮没有证明它是 484 格错误的唯一原因。其他错误及工作簿部件保真度均未进一步归因/验收。
- Go Excelize 和 Werkbook 只是本轮测试的 Go 候选，不据此断言不存在其他 Go 计算器。

【Office 隔离计算阶段计时】
- Excel COM 启动 4,119 毫秒；同一个实例连续处理五份未重算副本，单份“打开+计算+保存”耗时为 1,197.1、262.8、281.6、292.9、275.0 毫秒，中位数 281.6 毫秒。首份包含首次文件打开成本；后四份计算本身为 15.0–19.2 毫秒。
- WPS COM 启动 2,131 毫秒；同一个实例连续处理五份，单份“打开+计算+保存”耗时为 413.3、266.6、265.8、259.1、256.8 毫秒，中位数 265.8 毫秒。首份包含首次打开成本；后四份计算本身为 23.2–24.6 毫秒。
- 以上 COM 启动和多份复用时间与 Rust CLI 的单次进程时间口径不同，不能将中位数直接当作完整 S1 DAG 的加速比例。完整 DAG 单次观察见前节。

【结论与后续】
- 本样本中 Excel/WPS 的 S1 公式结果与问题记录满足既定对拍口径。Formualizer 速度明显，但存在文本结果及一条问题记录差异；当前不能替代 Office 重算。两个 Go 候选均未达到整本重算所需的结果和写回契约。
- 若 S1 明确要求本轮重算，建议后续在独立 sidecar 中按运行系统显式选择引擎：Windows 优先 Excel COM、按安装情况回退 WPS；Linux 仅在显式触发且 LibreOffice 已安装时调用 headless LO，缺失时报告“该功能需要外部引擎”。本轮未安装或验证 Linux LO。
- Office 启动成本占单文件隔离调用的大头；后续实现应评估 sidecar 按批次复用一个 Office/LO 实例，但必须维持每个输出的缓存刷新验证和失败隔离。
- 本轮仅一组真实模板/输入；还需覆盖更多真实模板、输入格式、公式依赖和 S1 输出结构，再确认 S1-F01。`audit-core/MIGRATION_INVENTORY.md` 中 S1-F01 仍保持“未验证”。
