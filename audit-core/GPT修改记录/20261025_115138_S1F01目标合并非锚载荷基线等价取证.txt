## 验证

- 样本与口径：2026-07-31 批次单位贷款模板族 7 本带缓存审核副本；模板 Defined Names 校验区域_001..004 展开 4 个复制区，交叉核对 5,487 区内格、1,072 个复制公式、55 个区内批注，与既有 `s1_formula_copy_candidate_umya_windows_native_20261025.json` 口径一致；映射按既有配方使用 config-real 配置的字节级临时副本（无"模块化功能"表时两侧均按内置默认解析）。
- 结果（7/7 一致）：每本原始目标簿 855 个合并非锚载荷，复制区内 0、区外 855，31 个载荷合并区域、37 个合并区域总数；Python 基线（`copy_formula_ranges_from_template`，本质 openpyxl load+修改+save）写后载荷保留 0/855、新增 0；纯 openpyxl load+save 保留 0/855、新增 0；两条路径输出的合并区域均 37→37 不变；Python 基线输出非空公式缓存为 0（openpyxl 保存不写缓存，与既有 Umya 报告 `python_formula_cache_nonempty_count: 0` 一致）；7/7 输入字节未变。
- 结论：既有 Python 产品基线本来就不保留这些载荷；openpyxl worker 的丢弃与基线逐格等价。守卫的目标侧全局检查防御的内容损失与已验收 Python 行为完全相同；但即使预检放行，共享读回校验器仍会在这些单元格报 `unmodified cell value changed`，因此需要 main 侧计划级 opt-in 同时覆盖预检与读回校验。
- 共享能力请求已按"接口、当前阻塞、期望行为、测试证据、复现方式"格式落盘；本轮不修改共享 crates，也不假定 main 已收到消息。
