## 四、版本编号规则

### 整包产品发布版本（用户确认：2026-09-30）

窗口标题、关于页面及 Windows/UOS 可执行文件使用同一个整包版本，
唯一来源为 `VERSION_MANIFEST.json` 的 `product.version`。
清单保存四段数字 `YY.MAJOR.MINOR.PATCH`，展示时加大写 `V`。
初始发布基线为 `V26.1.0.0`，表示 2026 年发布的第一个大版本。
当前整包版本为 `V26.1.7.3`，具体版本始终以 MANIFEST 为准。

- 年份：发布年份的末两位数字；每年首个大版本从 `YY.1.0.0` 开始。
- 大版本：新增大的平台系统或系统级能力时递增，中版本和小版本归零。
- 中版本：现有 S1/S2/S3 新增某项功能时递增，小版本归零。
- 小版本：修复缺陷或修改局部逻辑时递增。
- 示例：修复缺陷为 `V26.1.0.1`；新增 S1/S2/S3 功能为 `V26.1.1.0`；新增大的平台系统为 `V26.2.0.0`。
- 每次发布按实际变化更新清单与产品发布 CHANGELOG；重打相同代码包不自动升级版本。
- 产品发布版本与以下功能/配置组件的 SemVer 独立，不批量更改无关组件版本。

### 功能与配置组件版本

统一 `vMAJOR.MINOR.PATCH`：

- **PATCH**（v1.4.2 → v1.4.3）：Bug 修复、内部实现修复、性能优化、
  安全保护；不改变外部业务契约、不改变配置结构。
- **MINOR**（v1.4.2 → v1.5.0）：新增向后兼容功能、可选能力、规则能力、
  兼容字段；原有业务仍可继续运行。
- **MAJOR**（v1.x.x → v2.0.0）：不兼容业务语义变化、配置结构重大变化、
  接口契约破坏性变化、输入输出协议重大变化。

## 五、版本升级判断

修改完成后自问：

1. 外部行为契约（输出列、审核结论语义、文件协议）变了吗？
   破坏性变化 → MAJOR；新增可选项且默认行为不变 → MINOR；否则 PATCH。
2. 配置结构（Sheet/表头/列语义）变了吗？旧配置仍可读 → 相关功能可
   MINOR；要求配置同步迁移 → MAJOR 或另发迁移说明。
3. 只有一处内部实现修复且用户可见行为不变 → PATCH。

拿不准时保守升 MINOR 并在 CHANGELOG 写明理由；**禁止不记录就改版本**，
也禁止把无关组件一起升版本。

## 六、功能版本与配置版本独立（铁律）

- 只改功能代码（如 S2 环比算法修复）→ S2-F01 升 PATCH，S2-CFG-01 不动；
- 只改配置内容（如调整某条规则、某档警戒）→ S2-CFG-01 升 PATCH，
  S2-F01 不动；
- 两者都改 → 各自分别升级；
- 禁止"功能升级了，相关配置一起加版本"。

## 七、CHANGELOG 写法

每个组件目录一个 `CHANGELOG.md`，新记录追加在文件顶部基线条目之后：

```markdown
## v1.0.1 — YYYY-MM-DD HH:MM

变更类型：Bugfix | Feature | Breaking | Config | Baseline

前版本：v1.0.0
新版本：v1.0.1

修改内容：
- ...

影响文件：
- ...

配置影响：
- 无（或 Sx-CFG-xx vX → vY）

相关配置：
- S2-CFG-01 v1.0.0

测试：
- 定向 ...；core 全量 ...

GPT修改记录：
- GPT修改记录/xxxx.txt

Git提交：
- <hash>（未提交则写"未提交"）
```

## 八、VERSION_MANIFEST 更新规则

- `VERSION_MANIFEST.json` 是**当前版本的唯一权威清单**：版本变更必须
  先（或同时）改它，再写 CHANGELOG；
- 新增/删除组件、改实现路径、改配置文件映射时同步维护；
- 结构变更（新增字段）须同步更新 `core/tests/test_version_manifest.py`
  的守护断言；
- 版本号只写 `X.Y.Z` 数字（文件内），用户交流时加 `v` 前缀。

## 九、GPT修改记录联动

每份 `GPT修改记录/YYYYMMDD_HHMMSS_*.txt` 必须新增【组件版本】段：

```
【组件版本】
系统：S2 报表采集系统
影响功能：S2-F01 执行报表规则 v1.0.0 → v1.0.1
影响配置：S2-CFG-01 报表采集系统配置 v1.0.0 → v1.0.0（未变）
未修改的相关组件：S3-*（全部未动）
版本升级原因：Bugfix（百分数环比），未修改业务配置。
```

纯治理/文档类修改（如建立版本体系本身）写"不升级"。

## 十、禁止事项

1. 禁止伪造历史 SemVer（不得倒推 v0.x / v2.x 历史）；
2. 禁止把 3.0~3.3、period_v2 当版本号使用或据此升级版本；
3. 禁止为版本更新修改无关组件；
4. 禁止在 `版本管理/` 存放源代码副本、配置工作簿备份、运行输出、
   pytest temp、编译产物——它不是备份仓库；
5. 禁止只改 CHANGELOG 不改 MANIFEST（或反过来）；
6. 禁止改配置文件名、加配置内版本 Sheet 来"配合"版本体系（另行迁移）；
7. 禁止跳过【组件版本】字段提交 GPT修改记录；
8. **禁止用源码名管理版本**：当前活跃源码的目录/包/文件名必须表达
   业务职责（`systems/s2_report_collection/`、`expression_lae.py`），
   不得使用 `period_v2`、`xxx_v3`、`new_*`、`final2`、`legacy_*` 等
   历史版本式命名；版本统一由 VERSION_MANIFEST + CHANGELOG + Git 管理；
   迁移期的临时兼容 wrapper 完成后必须删除，不得长期保留；
9. 禁止为目录归位复制业务实现形成双实现——每项业务能力只有一个正式
   实现，迁移只允许 `git mv` + import 更新。

## 附：每次修改的固定流程

修改前：识别系统（S1/S2/S3）→ 识别功能（Sx-Fxx）与配置（Sx-CFG-xx）
→ 读 `VERSION_MANIFEST.json` 确定修改前版本。
修改后：判断 PATCH/MINOR/MAJOR → 更新 MANIFEST → 更新受影响组件
CHANGELOG → 新增 GPT修改记录（含【组件版本】）→ 最终报告列明
"哪些组件从什么版本升到什么版本"。
