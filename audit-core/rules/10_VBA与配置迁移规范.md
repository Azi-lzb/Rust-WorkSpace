# VBA 与配置迁移规范

本规则只在新 VBA 项目迁移、旧配置迁移或用户明确要求复核既有迁移时加载。项目硬约束见 `AGENTS.md`，配置执行性复核见 `rules/06_VBA复刻与配置复核.md`，测试流程见 `rules/07_测试与发布.md`。

## 默认目标

迁移应保留原工具的业务逻辑、数据口径、规则语义和用户工作流；技术实现可以重写。未经用户明确确认，不得删步骤、合并不同业务口径、改触发条件/阈值/单位/频度/筛选语义，或以简化代码为由减少业务能力。

迁移中发现可简化项可以提出建议，但不能自行实施。已完成并验收的迁移，除非有缺陷、对拍差异、配置不可执行或用户明确要求，不要为追求结构整齐重新迁移。

## 配置来源与映射

- 旧 VBA/Excel 存在稳定配置时，默认复用其内容。允许拆表、合表、改列名或显式化隐含字段，但必须记录旧来源到新结构的映射。
- 原始规则数量用于检查漏迁，不是未来生产配置的固定上限。样例/测试/垃圾行、用户确认的增删以及数量变化都应有依据。
- 每次迁移建立映射账，至少写明：源工作簿/模块/Sheet、源数量与排除项、旧 Python 模块和配置位置（作为来源映射）、字段/编号映射、拆并关系、启停数量、用户确认变更、未迁能力及验证方式。

## 隐含语义与异常

迁移前检查业务语义是否藏于 Sheet/模块名称、执行顺序、日期、频度/批次、单元格位置、名称管理器、颜色/批注、隐藏状态、表名选择、VBA 分支或文件命名。

对 VBA 病句、可疑公式、缺失 token、正则错槽、测试行混入、长期未执行逻辑或历史口径冲突：先呈现原始内容、疑点和证据，给出人工修改候选；未经用户确认，不自动替换、修正或把“语法合法”当成“业务正确”。

## Rust 落点与执行性

每类新迁入配置均须有 Rust 读取、检查、执行和测试落点。启用规则必须“进入执行链”或“明确报告失败”，解析失败不得静默跳过；具体规则见 `rules/06_VBA复刻与配置复核.md`。配置检查只读，不回写或自动修复工作簿。

技术选型遵循 workspace 根 `AGENTS.md` 和规则 13：calamine/OOXML 读取、rust_xlsxwriter 新建、ExcelEditPlan/ExcelModifier 修改；只允许公式重算和同类格式转换显式调用独立 sidecar。旧 Python/Office 调用只作为行为发现材料，不得复用为主路径。

## 验收与差异说明

按以下顺序组织证据：

1. 数量对账：解释源数量、排除/业务增删与当前承载数量。
2. 结构及编译检查：证明启用配置可解析、可执行或明确失败。
3. 关键规则测试：覆盖触发条件、过滤条件、边界、单位和缺值语义。
4. 同一数据的 VBA/黄金基线对拍：比较行身份、触发与跳过、计算过程、说明、数值口径和筛选结果。
5. 必要的平台验收：按 `rules/02`、`rules/07` 执行真实计算环境测试。

差异逐项分类为：明确 Bug 修复、用户确认的业务调整、平台语义差异、配置迁移差异、数据差异、未支持、待确认或回归缺陷。不得用“基本一致”或“数量接近”代替说明。

## 迁移记录

迁移完成后在 `GPT修改记录/` 记录来源、Python 落点、数量对账、字段映射、排除行、用户确认的删改、测试/对拍结果、未完成项和回滚方式。若用户明确决定简化，需标明这是业务决定而非漏迁。
